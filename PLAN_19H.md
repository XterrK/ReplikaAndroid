## 0.4 ОБНОВЛЕНИЕ 4 — пунктуация входит в точность транскрибации (перекрывает строку про нормализацию в §0.2)

**Эксперт кейса подтвердил: в точность транскрибации входит пунктуация.** Фраза «мы нормализуем ваш JSON», видимо, означала техническую нормализацию (пробелы, формат), а не удаление знаков.

**Решения:**
- **Остаёмся на GigaAM v3 E2E RNNT.** Она выдаёт пунктуацию и регистр по акустике (интонации), это лучше любого внешнего пунктуатора по тексту. A/B «базовая v3 RNNT без пунктуации» из §0.2/§3.4 **отменяется**. Базовую v3 RNNT имеет смысл рассматривать только как источник слов при сохранении пунктуации E2E, а это двойное время ASR — не делать.
- **Английский:** Parakeet TDT v2 тоже выдаёт пунктуацию и регистр, выбор подтверждается.
- **GigaAM-Multilingual CTC** (без пунктуации) **понижается**: для неё нужен отдельный пунктуатор, в эти 19 часов это не окупится.

**Главные рычаги пунктуации (добавить к задаче D):**
1. **Длинный контекст.** Модель ставит знаки внутри куска, который ей дали. Короткие срезы «VAD × turn» дают лишние точки в конце, пропущенные запятые и заглавную букву в середине фразы. ASR по целым VAD-сегментам (задача D) улучшает и слова, и пунктуацию.
2. **Разрез сегмента по смене говорящего** (на границе слова): первая часть часто остаётся без конечного знака, вторая начинается со строчной. Пост-правило:
   - реплика без конечного знака получает `.` (или `?`, если E2E поставила `?` на границе разреза, — сохранить);
   - первая буква реплики заглавная;
   - запятая или тире, оставшиеся в конце реплики после разреза, заменяются на `.`.
   Каждое правило включать только при выигрыше на стенде.
3. **Разрез > 20 с** делать в паузе (это уже в плане): разрез посреди фразы ломает пунктуацию вокруг шва.
4. **Числа:** E2E пишет цифрами («25», «10:30», «5%»). Как это считает жюри, неизвестно. Оставить цифры (это естественная орфография эталона «с пунктуацией»), но в стенде считать оба варианта.
5. **LLM как корректор пунктуации — только как эксперимент.** В «ограниченном» режиме LLM может менять только знаки и регистр; если последовательность слов (без учёта регистра) изменилась, берётся исходный текст. Включать, лишь если пунктуационная метрика на стенде растёт, а RTF терпим. Скорее всего не окупится, так что низкий приоритет.

**Стенд (§4.2) — новые метрики:**
- **WER «как есть»:** регистр и знаки остаются, знак приклеен к слову («день!» ≠ «день»). Это наиболее вероятный вариант жюри.
- **WER с пунктуацией как отдельными токенами** (`день !`).
- **Punctuation F1** по знакам `. , ? ! — :` и **точность регистра** первой буквы.
- WER без пунктуации остаётся для диагностики: показывает, где ошибка в словах, а где в знаках.
- Целевая функция §4.4: в слагаемом ASR использовать **WER «как есть»**.

**Переспросить у организатора одним сообщением:**
> Уточните, пожалуйста, как считается WER с пунктуацией: учитывается ли регистр; знак считается частью слова или отдельным токеном; «ё» и «е» различаются; числа сравниваются цифрами или словами?

## 0.3 ОБНОВЛЕНИЕ 3 — тест на ARM-эмуляторе, размер APK не важен (перекрывает всё про «4 ГБ»)

Ограничения «4 ГБ RAM» нет, его написал участник. Точно известно: **проверка на эмуляторе Android с ARM-процессором**, **размер APK значения не имеет**.

**Что это значит для конвейера:**
- **Только CPU.** У эмулятора нет NPU/DSP, NNAPI и QNN бесполезны, GPU — трансляция хоста. Всё ускорение — потоки CPU и лёгкие графы.
- **Число ядер неизвестно** (у AVD обычно 2–4 vCPU, может быть 8). Потоки ASR/диаризации выставлять от `Runtime.getRuntime().availableProcessors()`, например `min(4, max(1, cores − 1))`, а не фиксированные 2. Это напрямую влияет на RTF (10 баллов).
- **Термоконтроль:** на эмуляторе thermal status обычно `NONE` или недоступен. Проверить, что ожидание охлаждения никогда не блокирует обработку, если API ничего не возвращает.
- **RAM у AVD по умолчанию бывает 2–4 ГБ.** Лимита от организаторов нет, но OOM на эмуляторе означает 0 баллов. Загрузку моделей по стадиям (уже есть) оставить. Проверить проход 3 файлов подряд без перезапуска приложения.
- **Хост эмулятора — скорее всего Mac на Apple Silicon** (самый частый способ запустить ARM-образ). На M1 нет `i8mm`/SVE. Всё нативное должно запускаться **без SIGILL** на базовом ARMv8.2 (sherpa/ORT делают runtime-dispatch). Если будете собирать llama.cpp, **не** задавать жёстко `+i8mm`: использовать runtime-dispatch CPU-вариантов или базовый `armv8.2-a+dotprod`.
- **16 KB page size:** свежие ARM-образы Android 15+ бывают с 16 КБ страницами. Ваши `.so` проверены только статически, поэтому **прогнать APK на образе «16 KB Page Size»** (есть в SDK Manager для API 35/36).
- **Импорт файлов на эмуляторе:** эксперты, скорее всего, перетащат файлы в окно эмулятора (они попадают в `Download/`) или зальют через `adb push`. Проверить, что системный выборщик видит файлы из `Download/` и что поддерживаются **WAV, MP3, M4A/AAC, OGG/Opus, FLAC**, моно и стерео, 8/16/44.1/48 кГц.
- **Как тестировать у себя:** на Windows x86 ARM-образы почти не работают. Варианты: (1) у кого-то из команды есть Mac M-серии → arm64 AVD; (2) иначе x86_64-образ (у вас есть `allInOneQa`) как прокси по функциональности плюс физический arm64-телефон по скорости. RTF на эмуляторе, скорее всего, будет хуже телефона: закладывать запас.

**Что это значит для моделей (размер не важен):**
- **ASR:** проверить на стенде **FP32-энкодер GigaAM v3** против INT8. Если WER лучше, а RTF на CPU приемлемый, ставить FP32. Под трансляцией INT8-ядра не всегда быстрее FP32. **Мерить, не гадать.**
- **GigaAM-Multilingual Large CTC (600M)** больше не отсекается по размеру: host A/B на нормализованном WER — полноценный кандидат. Но RTF в 2–3 раза хуже v3, поэтому брать только при заметном выигрыше.
- **Диаризация:** можно брать эмбеддеры покрупнее (TitaNet-large, ERes2Net-large). Выбор только по DER и времени.
- **Английский:** Parakeet TDT 0.6B v2 без колебаний (вместо Moonshine).
- **LLM:** если делать, можно взять QVikhr-3-1.7B вместо 0.6B, но приоритет LLM по-прежнему низкий (§0.2).

**Главный компромисс теперь не размер, а RTF на CPU эмулятора.** Целевая функция стенда (§4.4) учитывает скорость; каждое «увеличение модели» проверять по ней.

## 2. Оценка текущего состояния

### Сильные стороны (не ломать)
- Настоящий on-device конвейер: sherpa-onnx 2.0.1, GigaAM v3 E2E RNNT int8, Silero VAD, Pyannote seg 3.0 + 3D-Speaker.
- GigaAM v3 E2E выдаёт **пунктуацию, регистр и цифры** (ITN), то есть пункт «восстановление пунктуации» уже закрыт.
- All-in-One APK работает офлайн, provisioning надёжный, есть WorkManager, отмена, термоконтроль.
- Плеер с переходом к реплике, правки, Smart Review, экспорт TXT/SRT/JSON: UX сильный.
- Есть метрики WER/CER/DER в коде (`Benchmark.kt`) и культура evidence.

### Критические дыры (в порядке влияния на баллы)
1. **Нет LLM**, а она в обязательных требованиях.
2. **JSON не в формате жюри.** Автоматический скоринг может просто не распарсить файл, и тогда 0 баллов за точность.
3. **Auto-диаризация пересегментирует.** Причины по данным отчётов:
   - embedding-модель `eres2net_base … zh-cn` обучена на китайском 3D-Speaker; на русском качество не мерили;
   - complete linkage + один порог: даже при пороге 0.85 получилось 5 вместо 4, значит эмбеддинги «шумные» на коротких кусках;
   - нет пост-обработки: слияния мелких кластеров, минимальной суммарной длительности спикера, сглаживания коротких вставок.
4. **ASR работает на срезах «VAD × turn».** Короткие срезы дают модели мало контекста, а жёсткий разрез 20 с режет слова. Для диалогов с частой сменой реплик это прямые потери WER.
5. **VAD `min_speech=0.25 s`, threshold 0.5** может выкидывать короткие реплики («Да.», «Угу», «Нет!»). В диалогах это частые delete-ошибки, и Ultra-критерий прямо про «короткие реплики и перебивания».
6. **RTF не измерен** на текущей версии. `windowShiftRatio=0.1` у Pyannote означает 10-кратное перекрытие окон, это дорого.
7. **Git:** V1.4–V1.6 не закоммичены.

### Чего мы не знаем и надо спросить у организаторов (5 минут, огромная ценность)
Написать в чат хакатона:
1. Как нормализуется текст перед WER: регистр, пунктуация, `ё/е`, **цифры или слова** («25» vs «двадцать пять»)?
2. Как считается точность диаризации: DER (с каким collar), cpWER/WDER или совпадение speaker_id по репликам?
3. Как считается точность временных меток?
4. На каком устройстве меряют RTF (модель телефона / SoC / RAM)? Входит ли в RTF время LLM?
5. Формат и длительность тестовых записей, сколько говорящих примерно, есть ли наложения и шум?
6. Засчитывается ли LLM, если она используется для протокола/резюме встречи, а не в критическом пути ASR?

Ответы на 1 и 4 напрямую определяют, какой режим ASR и какую нормализацию ставить по умолчанию.

## 3. Решения по моделям (исследование)

### 3.1 ASR — **оставить GigaAM v3 E2E RNNT как основной**

| Кандидат | Вывод |
|---|---|
| **GigaAM v3 E2E RNNT** (текущая) | Лучший открытый русский ASR с пунктуацией и ITN. ~5.35% WER FLEURS-ru (community GGUF), у вас 4.6–5.1%. Оставить. |
| GigaAM v3 RNNT (без E2E) | В официальной таблице GigaAM среднее 8.3 против 11.2 у E2E RNNT, но на нормализованном тексте. Лексически лучше, однако без пунктуации и цифр. **Имеет смысл, только если жюри считает WER на нормализованном тексте.** Тогда схема «v3 RNNT для слов + пунктуация отдельно» (см. 3.4). |
| **GigaAM-Multilingual Large CTC 600M** (июль 2026, MIT) | По карточке RU FLEURS 3.0 / CV 5.1 / internal 6.0 (лучше Whisper-large-v3). **Но:** только char-CTC, без пунктуации и ITN; в sherpa-onnx официальной RU-конверсии нет (есть только узбекский fine-tune); с v3 на одном протоколе не сравнивали; в 2.5 раза больше энкодер, то есть медленнее. Официальный `model.to_onnx()` есть. **Вывод:** только host A/B на своих диалогах; интегрировать, лишь если выигрыш ≥ 10% относительных WER на нормализованном тексте и RTF приемлем. Скорее задача на после хакатона. |
| Qwen3-ASR 1.7B / 0.6B | RU FLEURS ~6% у 1.7B, хуже GigaAM и тяжелее. Нет. |
| Parakeet TDT v3, Whisper, T-one, Vosk | Уже проверены или хуже на русском. Нет. |
| INT8 → FP32 энкодер v3 | Проверить на ПК: если FP32 даёт ≥ 3% относительного выигрыша, а RTF на телефоне терпимый, это кандидат. APK вырастет примерно на 700 МБ. |

**Главные рычаги WER — не модель, а конвейер:**
1. **ASR на VAD-сегментах, а не на срезах turn.** Длинный контекст (до 20–25 с, разрез в тишине) лучше распознаётся. Затем **токенные таймкоды** sherpa (`OfflineRecognizerResult.timestamps` для transducer) собираются в слова, каждое слово получает спикера по пересечению с turns диаризации, и сегмент режется по смене спикера на границе слова. Это одновременно улучшает WER, диаризацию на уровне слов и таймкоды. *Проверить:* что GigaAM-конверсия отдаёт timestamps (шаг кадра у GigaAM 40 мс).
2. **Разрез > 20 с** делать в точке минимальной энергии или VAD-паузы внутри последних 3–5 с, а не жёстко.
3. **VAD под короткие реплики:** sweep `threshold 0.35–0.5`, `min_speech 0.08–0.25`, `min_silence 0.1–0.3`, pre-roll 100–250 мс. Считать delete-ошибки отдельно.
4. **Нормализация под скоринг** (после ответа организаторов): режим «цифры → слова» (ITN-обратка) и `ё→е`, если эталон такой. Делать флагом.
5. **Hotwords** (modified_beam_search + hotwords): домен неизвестен заранее, эффект мал. Низкий приоритет.
6. **Шумоподавление GTCRN** (есть в sherpa, около 0.5 МБ): включать **только** при низком оценённом SNR. На чистой речи шумодав почти всегда ухудшает WER. Проверять на стенде.

### 3.2 Диаризация — **поменять embedding-модель + своя пост-кластеризация**

Embedding-кандидаты (все есть в релизе sherpa-onnx `speaker-recongition-models`; точные имена файлов сверить на странице релиза):
- `wespeaker_en_voxceleb_resnet34_LM.onnx` (~26 МБ). Тот же тип эмбеддинга, что в pyannote community-1. **Фаворит.**
- `3dspeaker_speech_campplus_sv_en_voxceleb_16k.onnx` (~28 МБ), быстрый.
- `wespeaker_en_voxceleb_CAM++_LM.onnx`
- `nemo_en_titanet_small.onnx` / `nemo_en_titanet_large.onnx`: TitaNet показывает сильный DER на CH109/AMI.
- `3dspeaker_speech_eres2netv2_…` / `eres2net_large_…`
- текущий `eres2net_base_zh-cn` как baseline.

VoxCeleb — это мультиязычные интервью, такие модели гораздо менее зависимы от языка, чем модель на китайском 3D-Speaker.

**Алгоритм (поверх текущего sherpa API, без замены всего стека):**
1. sherpa-диаризация с выбранным эмбеддером, порог подбирается на стенде для каждой модели (sweep 0.3–0.95).
2. **Over-cluster-then-merge:** для каждого найденного кластера посчитать центроид через `SpeakerEmbeddingExtractor` (усреднить эмбеддинги окон 1.5 с / шаг 0.75 с только по «чистым» участкам ≥ 1 с без overlap). Затем итеративно сливать пары с cosine sim > τ.
3. **Оценка числа спикеров** по eigengap матрицы сходства центроидов (NME-SC-подобно), ограничение `K ≤ 8`.
4. **Мелкие кластеры:** суммарная длительность < max(2 с, 3% записи) → переназначить ближайшему по центроиду.
5. **Сглаживание:** вставка < 0.4–0.6 с другого спикера между двумя одинаковыми → слить; `minDurationOff` подобрать.
6. **Словный уровень** (см. 3.1-1): спикер назначается словам, а не кускам.
7. В экспорте **никогда нет `-1`**: неоднозначное назначается ближайшему по времени или центроиду.
8. Перенумерация `speaker_1..N` по первому появлению (уже есть, просто сделать 1-based строкой).

**Если останется время (Ultra):** Sortformer 4spk v2/v2.1 (NVIDIA) как end-to-end диаризатор до 4 спикеров. ONNX-экспорты есть (INT8 ~129 МБ), но в sherpa-onnx поддержки нет: нужен свой ORT-инференс и пост-обработка. Конфликт двух `libonnxruntime.so` (sherpa + свой ORT) вероятен. **Не в эти 19 часов**, только host-эксперимент.

Pyannote segmentation 3.0 оставить. `windowShiftRatio` поднять с 0.1 до 0.25–0.5, если DER не растёт: это сильно ускоряет.

### 3.3 Локальная LLM — **llama.cpp + маленькая русскоязычная модель, вне критического пути**

**Рантайм:** `llama.cpp` через NDK/CMake с официальным модулем `examples/llama.android` (pinned commit). У команды уже был опыт сборки whisper.cpp JNI, паттерн тот же. Флаги для arm64: `GGML_CPU_ARM_ARCH=armv8.2-a+dotprod+i8mm` (с fallback). Готовые Kotlin-обёртки (Llamatik, llmedge) быстрее подключить, но с ними меньше контроля. **ONNX Runtime GenAI не брать:** конфликт `libonnxruntime.so` с sherpa.

**Модель (GGUF Q4_K_M):**
1. **QVikhr-3-1.7B-Instruction-noreasoning** (~1.1 ГБ): Qwen3-1.7B, дообученная на русском (Ru Arena 59.2 против 49.7 у базы). **Основной выбор.**
2. Vikhr-Qwen-2.5-1.5B-Instruct (~1 ГБ, Apache-2.0) или Vikhr-Llama-3.2-1B-instruct (~0.8 ГБ) как запасные.
3. Qwen3-0.6B (~0.4 ГБ), если APK или RAM поджимают.
4. Gamayun 1.5B (декабрь 2025, сильный на MERA): проверить, есть ли GGUF.

**Где использовать LLM (WER не трогает):**
- **«Протокол заседания»** (идеально ложится в легенду кейса): участники, повестка, ключевые тезисы по спикерам, принятые решения, задачи (кто / что), открытые вопросы. Экспорт в TXT/MD рядом с JSON.
- **Подсказка имён спикеров** по контексту («Барсик, что скажешь?» → speaker_2 = Барсик). Только для UI; `speaker_id` в JSON остаётся `speaker_N`.
- **Вопросы к стенограмме** (чат по записи), как бонус к UX.
- *Экспериментально, по умолчанию выключено:* LLM-подсказки для Smart Review (подозрительные слова). **Не** переписывать текст автоматически: маленькие LLM на русском почти всегда ухудшают WER.

**Важно для RTF:** LLM запускается **после** готовой стенограммы, отдельной кнопкой или фоновым шагом после публикации JSON. ASR и диаризацию перед загрузкой LLM выгрузить (общий `ModelManager.gate`). В UI показывать прогресс и токены/с. Контекст: для длинной записи map-reduce по кускам ~1500 токенов.

**Размер APK:** ~306 МБ + ~1.1 ГБ = ~1.4 ГБ. Установка через adb или файл это выдерживает. Альтернатива: LLM отдельным файлом, импортируемым в приложение. Но «все модели должны быть на устройстве к моменту проверки», поэтому надёжнее всё в одном APK. Проверить, что AGP/zipalign нормально собирает APK > 1 ГБ (в assets хранить без сжатия, `noCompress += "gguf"`).

### 3.4 Если жюри считает WER на нормализованном тексте
Тогда сравнить на стенде:
- (a) E2E RNNT как есть + нормализация вывода;
- (b) v3 RNNT (лексически точнее) + пунктуация/регистр «бесплатно» из E2E прогона (выравнивание по словам), что удваивает время ASR;
- (c) v3 RNNT + пунктуация от LLM в «ограниченном» режиме: LLM может только вставлять знаки и менять регистр; если множество слов после LLM ≠ исходному, берётся fallback.

Выбрать по числам. Если разница < 3% относительных, оставить (a).

### 3.5 Английский (второй приоритет) — НОВОЕ
**Схема:** определение языка → маршрутизация на нужную ASR-модель.
- **Определение языка:** `SpokenLanguageIdentification` из sherpa-onnx (на энкодере/декодере Whisper tiny, ~40–75 МБ int8). Считать по 2–3 первым VAD-сегментам на файл или по каждому VAD-сегменту, если допускаем смешанный язык. Порог уверенности: при сомнении — русский (первый приоритет).
- **Английский ASR, варианты:**
  1. **NVIDIA Parakeet TDT 0.6B v2 (English) int8**, есть в sherpa-onnx: одна из лучших открытых английских моделей, выдаёт пунктуацию и регистр, ~0.6 ГБ. Лучшее качество, но APK станет больше.
  2. **Moonshine base** (sherpa-onnx, ~60M параметров, ~0.25 ГБ): заметно хуже Parakeet, но лёгкая и быстрая.
  3. Parakeet TDT 0.6B **v3** (мультиязычная, вы её уже мерили на RU): одна модель на оба языка, но для RU хуже GigaAM. Использовать только для EN-сегментов.
  Рекомендация: **Parakeet TDT v2** (размер APK не важен, §0.3).
- Модели EN загружаются **только** если определён английский (экономия RAM и времени на эмуляторе).
- Стенд: добавить 10–20 EN-диалогов (симуляция из Common Voice EN / LibriSpeech + пара своих записей), WER считать отдельно по языкам.
- Embedding-модели диаризации на VoxCeleb (§3.2) и так англоязычные, то есть замена эмбеддера помогает обоим языкам.
- В UI: язык авто / RU / EN (ручное переопределение), язык в JSON не добавлять (формат строгий), но показать в интерфейсе.

### 3.6 Записи звонков — НОВОЕ
Тест-кейсы «будут разные», значит почти наверняка будет телефонное аудио.
- **Стерео с разными каналами:** если в файле 2 канала с низкой корреляцией (каждый абонент на своём канале), диаризировать **по каналам**: это почти идеальная диаризация бесплатно. Сейчас `AudioDecoder` усредняет каналы, и эта информация теряется. Добавить детектор (корреляция каналов + энергия по VAD на каждом канале) и режим «канал = говорящий».
- **8 кГц / AMR / Opus / сильное сжатие:** апсемплинг до 16 кГц уже есть. Проверить на стенде: симулировать телефонный канал (полоса 300–3400 Гц, ресемпл 8 кГц, AMR-NB/Opus 12–16 kbps). GigaAM v3 обучалась в том числе на колл-центре, это плюс.
- VAD на телефонном аудио ведёт себя иначе: свой порог в sweep.
- «Реальное время» (живая расшифровка звонка) для автопроверки не нужно, проверяют импорт файла. Если останется время — только как демо-фича для защиты.

## 4. Стенд оценки — механизм «бесконечного улучшения»

Всё на ПК (Python 3.12, **тот же sherpa-onnx 2.0.1**, те же ONNX-файлы и параметры, что в Android). Цикл: агент меняет один параметр → прогон → строка в `results.csv` → оставляем, только если стало лучше на dev **и** не хуже на holdout.

### 4.1 Данные (без них ничего не измерить)
1. **Свои записи «заседаний котиков»** — самое ценное. Сценарии (5–10 шт., 2–6 «котов», 2–5 мин) пишет GLM/Kimi в стилистике кейса: мыши, пицца, кафедра, протокол, перебивания, короткие «Да!» / «Мяу-нет». Команда и друзья читают по ролям на телефон: тихо и громко, с шумом, с перебиваниями. Эталон = сценарий + ручная разметка таймкодов (или WhisperX/pyannote на ПК **только для черновой разметки эталона**, потом ручная правка).
2. **Симулированные диалоги:** склейка реплик разных спикеров из Common Voice RU / Golos / SOVA (`client_id` = спикер), паузы −0.3…1.5 с (10–15% overlap), шум и реверберация. Генерирует точные RTTM, тексты и таймкоды автоматически, сотни файлов.
3. **Синтетика TTS** (мультиголосовой русский TTS) как дополнительный стресс-тест тембров. Возможно, тестовые «котики» тоже озвучены TTS.
4. Разделить: **dev** (тюним) / **holdout** (смотрим только в конце, чтобы не переобучиться).

### 4.2 Скоринг (`tools/eval/score.py`)
На вход: наш JSON (формат жюри) + эталон (тот же формат). Выход:
- **WER** в трёх вариантах: raw; normalized (lowercase, без пунктуации, `ё→е`); normalized + числа словами. Плюс доли S/D/I отдельно: D говорит о VAD, S об ASR.
- **CER.**
- **DER** (pyannote.metrics или своя реализация из `Benchmark.kt`), collar 0 и 0.25, с оптимальным сопоставлением ID; **ошибка числа спикеров**.
- **cpWER** (concatenated minimum-permutation WER): лучшая метрика «текст + спикер», вполне вероятно, жюри меряет что-то похожее.
- **Таймкоды:** средняя |Δstart|, |Δend| по сопоставленным репликам, доля реплик с ошибкой > 250 мс.
- **RTF** = время обработки / длительность (host; отдельно с телефона).

### 4.3 Связь с Android
- Debug-интент или кнопка в диагностике: «обработать папку → сохранить JSON в /sdcard/Download/replika-eval/»; `tools/eval/pull_and_score.py` через adb.
- Перед каждым релизом: те же 5 файлов на телефоне и на ПК; расхождение WER > 0.5 п.п. означает баг переноса.

### 4.4 Цикл автотюнинга (отдать GLM/Kimi с бесконечными лимитами)
`configs/sweep.yaml` с параметрами: VAD (threshold, min_speech, min_silence, pre/post-roll), диаризация (embedder, threshold, τ слияния, min cluster share, smoothing), ASR (max segment, точка разреза, threads). Агент запускает `python tools/eval/run.py --config X`, читает `results.csv`, предлагает следующий шаг. **Целевая функция** (под веса баллов): `0.40·(1−WER) + 0.25·(1−DER) + 0.10·(1−tsErr) + 0.10·speed`. Каждые N итераций смотреть holdout.

## 6. Готовые задачи для Codex (копировать как есть)

**A. JSON по формату жюри**
> В `domain` экспорта добавь формат `JuryJson`: корневой объект `{"transcript":[...]}`, элементы `{"speaker_id":"speaker_<N>","start_ms":<int>,"end_ms":<int>,"text":"<string>"}`; N = 1-based по первому появлению; сортировка по start_ms; пустые тексты не выводить; speakerId=-1 назначать ближайшему по времени известному спикеру; UTF-8 без BOM, без лишних полей. Сделай его форматом по умолчанию для «Экспорт JSON», старый оставь как «Диагностический JSON». Покрой JVM-тестами (порядок, нумерация, -1, пустые, экранирование кавычек и переводов строк). Не трогай ML-конвейер.

**B. Локальная LLM**
> Добавь модуль на основе llama.cpp (официальный `examples/llama.android`, pinned commit, NDK 27.2, arm64-v8a) с Kotlin API `LlmEngine.load(path)`, `generate(prompt, maxTokens, onToken)`, `close()`. Модель GGUF (QVikhr-3-1.7B-Instruction-noreasoning Q4_K_M) кладётся в All-in-One assets без сжатия и провиженится как остальные модели (SHA в models-lock). После завершения транскрипции на экране записи появляется «Протокол заседания»: участники, тезисы по спикерам, решения, задачи, открытые вопросы. Генерация в WorkManager под общим ModelManager.gate, ASR/диаризация перед загрузкой выгружены, стриминг токенов в UI, отмена, map-reduce для длинных стенограмм (~1500 токенов на кусок). Экспорт протокола в TXT/MD. LLM НЕ влияет на текст стенограммы и JSON и не входит во время основной обработки. Добавь в diagnostics tok/s и время.

**C. Диаризация (сначала host, потом Kotlin)**
> В `tools/eval/diar_sweep.py`: для каждой embedding-модели из списка [текущая eres2net_base_zh, wespeaker_en_voxceleb_resnet34_LM, 3dspeaker campplus voxceleb, wespeaker CAM++_LM, nemo titanet_small, titanet_large] и порогов 0.3..0.95 шаг 0.05 прогоняй sherpa-onnx 2.0.1 OfflineSpeakerDiarization на dev, считай DER (collar 0/0.25) и ошибку числа спикеров. Затем реализуй пост-обработку: центроиды кластеров через SpeakerEmbeddingExtractor по чистым окнам 1.5 с/0.75 с, итеративное слияние по cosine > τ, оценка K по eigengap (K ≤ 8), переназначение кластеров < max(2 с, 3%) длительности, сглаживание вставок < 0.5 с. Подбери τ на dev, проверь на holdout. Результаты в results.csv. Потом перенеси пост-обработку в Kotlin (`domain/SpeakerRefiner.kt`, чистые функции) с JVM-тестами.

**D. ASR по VAD-сегментам + словное назначение спикеров**
> Проверь на ПК, что sherpa-onnx возвращает `timestamps` и `tokens` для GigaAM v3 E2E (nemo_transducer). Если да: измени планирование так, чтобы ASR шёл по VAD-сегментам (макс 20 с, разрез в точке минимальной энергии внутри последних 4 с, если сегмент длиннее), токены склеивались в слова (по `▁`), каждому слову назначался спикер по максимальному пересечению с turns диаризации, а реплика резалась при смене спикера на границе слова. start_ms/end_ms реплики = первое/последнее слово (+ небольшой отступ, подобрать на стенде). Сравни на стенде с текущим планировщиком: WER, cpWER, DER, ошибки таймкодов. Включать в Android только при выигрыше.

**E. Английский ASR + определение языка**
> Добавь в model pack (с SHA в models-lock) sherpa-onnx spoken language identification (whisper tiny int8) и английскую модель Parakeet TDT 0.6B v2 int8 (nemo_transducer). Перед ASR определи язык по первым 2–3 VAD-сегментам (порог уверенности; при сомнении — ru). Для ru используй GigaAM v3, для en — Parakeet; английские модели загружай только при необходимости, выгружай после. Добавь в настройках обработки выбор языка: Авто / Русский / English. Формат JSON не меняй. Добавь на стенде EN-набор и раздельный WER по языкам. Проверь проход на ARM-эмуляторе (или x86_64-прокси) без OOM при RAM AVD по умолчанию.

**F. Стерео-звонки: канал = говорящий**
> В `AudioDecoder` сохраняй каналы стерео-файла отдельно (кроме общего mono). Добавь детектор: если корреляция каналов низкая и речь по VAD на каналах в основном не совпадает по времени, предложи и по умолчанию примени режим «канал = говорящий»: VAD и ASR по каждому каналу, speaker_1/speaker_2 по каналу, сортировка по времени. Иначе — обычный конвейер. JVM-тесты на синтетическом стерео.

**G. Второй APK и удаление моделей**
> Доведи вариант без встроенных моделей («Lite»: скачивание моделей при первом запуске с проверкой SHA) и в All-in-One добавь в экране моделей «Удалить встроенные модели» с подтверждением и «Скачать заново». Основной APK для сдачи — All-in-One.

## 8. Долгосрочное развитие (после хакатона, для раздела «Дальнейшее развитие»)
1. **Fine-tune GigaAM v3** на русской разговорной речи (диалоги, совещания, телефония) + LoRA под домен; дистилляция в меньший энкодер для слабых телефонов.
2. **GigaAM-Multilingual Large CTC** как опциональный «точный режим» после host-сравнения; своя конверсия в sherpa (nemo_ctc metadata) и INT8.
3. **End-to-end диаризация** (Sortformer-класс) для ≤ 4 спикеров + классический конвейер для > 4; **target-speaker / separation** (MossFormer2/SepFormer-класс) для overlap.
4. **Аппаратное ускорение:** QNN (Snapdragon NPU, у sherpa есть QNN-бинарники), NNAPI/XNNPACK-профили, автоподбор потоков по big.LITTLE.
5. **Streaming:** онлайн-распознавание во время записи (GigaAM streaming / chunked RNNT) и инкрементальная диаризация.
6. **Персональные голоса:** enrollment участников (эмбеддинг из 10 с) и стабильные имена между записями (с явным согласием).
7. **Словные таймкоды и confidence** в UI: подсветка сомнительных слов, клик по слову = позиция в аудио, повторная обработка выделенного фрагмента.
8. **LLM-слой:** протоколы по шаблонам (совещание, интервью, лекция), поиск по библиотеке, извлечение задач в календарь (локально).
9. **Checkpoint ML-стадий**, чтобы не начинать заново после смерти процесса; потоковое чтение PCM в диаризации для длинных записей.
