# REPLIKA V1.3 — восстановление диаризации

## Статус

**Режим одного говорящего реализован отдельно. Исправление автоматического определения числа участников не подтверждено; прежний общий алгоритм clustering сохранён.** Запись vivo, на которой получилось 11 участников, отсутствует. Нельзя подменять её повторением короткого fixture.

## Аудит

Существующая конфигурация: Pyannote segmentation 3.0, windowShiftRatio .1, CPU threads 2; 3D-Speaker ERes2Net embedding (`zh-cn` в исходном имени модели), CPU threads 2; complete-linkage clustering по cosine dissimilarity, automatic threshold .5. minDurationOn .2 s, minDurationOff .5 s. Speaker IDs нормализуются по первому появлению в исходном clock; отрицательные ID остаются неизвестными. Приложение не получает внутренние embedding vectors из native diarization API, поэтому их численное распределение на записи пользователя не измерено. Языковое имя модели само по себе не доказывает причину ошибки.

[Исходник clustering закреплённой версии sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/csrc/fast-clustering.cc) подтверждает cosine dissimilarity и complete-linkage, `numClusters` для известного состава, threshold для automatic. [Исходник diarization](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/csrc/offline-speaker-diarization-pyannote-impl.h) показывает segmentation→embeddings→clustering. Встроенный процессор не выдаёт приложению независимый ground truth или достоверную идентичность человека.

Короткая речь раньше создавала неизвестные отдельные ASR-фрагменты, а не обязательно новый native speaker cluster. Эти два дефекта учитываются отдельно: planner не переименовывает реальные разные speaker IDs и не «чинит» число участников слиянием всех соседних голосов.

## Три режима

- **Один говорящий (`1`)**: один Turn 0..duration с ID 0, только VAD+ASR, без создания diarizer и без загрузки diar-моделей. Нужен явный выбор пользователя; автоматическое обнаружение монолога не заявлено.
- **Фиксированное число (`2..20`)**: штатный native `numClusters`, сохранённая пользовательская настройка Recording.expectedSpeakers. Порог .5 не используется для выбора числа. Если реальной речи/embedding points недостаточно, native не обязан изобретать недостающих участников; UI не создаёт пустых участников ради числа.
- **Автоматически (`-1`)**: native threshold .5 явно прописан, глобального cap числа участников нет. В UI указано, что число может быть неточным. Нет утверждения, что автоматический режим теперь надёжен для длинного русского монолога.

## Воспроизводимые эксперименты

`tools/benchmark_v13_host.py` и `docs/test-evidence/v1.3/host-diarization-probe.json`: Linux WSL x86_64, настоящие прежние weights. Русский публичный WAV 11.29 s и его контролируемое повторение 247.59 s дают одного участника на .5/.7/.85. Повтор не является независимой записью и не моделирует изменение положения телефона, тембра или фоновых шумов.

Публичный китайский fixture с ожидаемыми четырьмя участниками даёт 7/5/5 на .5/.7/.85. Изменение порога влияет на число, но не доводит этот пример до 4, а без time-aligned reference не даёт DER. Эти результаты — основание **не выпускать пороговое «исправление»**, а не доказательство исправности automatic.

Android-проверки включают существующий automatic/fixed4 эксперимент, стабильность ID, overlap и несколько минут в явном single. Отчёт тестов различает host и Android. Нельзя считать fixed4 ручной эталонной диаризацией каждого слова.

## Осталось

Не реализован и не принят новый automatic estimator числа участников. Нужны независимые естественные монологи и многоголосные записи, предпочтительно русские, с эталонными участниками/сменами, включая реальные короткие ответы и перекрытия. Затем сравнивать DER, false speaker splits/merges, распределения embedding distances, гипотезы и затраты памяти. Порог, фильтрация коротких кластеров и смена linkage не должны подбираться по одному случаю. Текущее состояние V1.3 — кандидат с безопасным явным single, а не закрытие критического automatic-багa.

## Завершённая Android-проверка

Финальный API35/x86_64 прогон: automatic .5 → 7, fixed4 → 4, automatic .65 → 7 на известном four-speaker fixture. Приёмка числа в automatic на этом примере **FAIL**, хотя smoke/configuration тесты прошли свои явно ограниченные assertions.

Дополнительный Android JNI-прогон повторённого русского decoded waveform **247.590 s** дал **1 участника / 42 turns**, load 440 ms, inference 77531 ms. Проверены нормализованные ID 0 и границы. Это контролируемая регрессия long mono; независимых записей здесь не появилось и дефект vivo не объявляется устранённым.
