## 2026-11-06T22:45:09+03:00 — пункт 1: контракт экспорта

- Обычный JSON — строгий JuryJson: только `transcript` и поля `speaker_id`, `start_ms`, `end_ms`, `text`. UTF-8 без BOM, без нормализации текста, регистра или пунктуации.
- Сначала отбрасываем пустые тексты и сортируем по start/end, затем назначаем неизвестных ближайшему известному интервалу (расстояние между краями; при равенстве — более ранний интервал). Нумеруем после назначения по первому появлению. Пустые строки не создают speaker IDs.
- Если известных спикеров вообще нет, все непустые реплики получают условный `speaker_1` только в строгом экспорте. Это fallback формата, не подтверждение diarization; исходные `-1` и warnings сохраняются в Room и диагностике.
- Старый расширенный JSON оставлен отдельным пользовательским выбором «Диагностический JSON», с отдельным `.diagnostic.json` файлом. Это доступный fallback прежнего формата; ML-флаги и модели не менялись.
- Кодирование вынесено с Main в Dispatchers.Default; получение Room snapshot остаётся транзакционным.
- Новые записи уже имеют expectedSpeakers=-1 (automatic); сохраняем этот default и прежние явные настройки записей. Automatic показывается первым в выборе; added UI regression фиксирует выбор.

## 2026-11-06T23:28:27+03:00 — пункт2: воспроизводимость и область оценки

- Корпус доступен без gated-доступа: immutable Langswap author CSV + publisher LFS hashes. Val→dev/test→holdout,77разных исходников; selection до inference. DER — proxy по utterance placement, не natural-dialogue speech-activity gold; ограничение сохраняется в каждом отчёте.
- Основной rawWER сохраняет пунктуацию/регистр/ё/числа; normalized, number-normalized, punctuationF1, case, cpWER, DER0/250 и timing coverage — отдельные метрики. Нулевой знаменатель →null.
- Для native DER используются сырые turns до export-only nearest-speaker projection; число native кластеров учитывается отдельно. В baseline ни text, ни expected K из manifest не входят в process; только глобальная настройкаautomatic=-1.
- SHA моделей проверяется каждый process, включая одинаковые size/mtime. Config, код, inputs, refs и сохранённые artifacts fingerprinted; повтор не перезаписывает исходные evidence, частичные попытки архивируются.
- Связь с Android реализована отдельным instrumentation bridge и CLI pull_and_score, без добавления файлового debug-intent в продуктовый UI. Это тот же productionWorker, только заранее staged audio/hash/id; refs остаются на host. QA cleanup затрагивает только своиUUID, не данные пользователя.
- Baseline выявил реальные v3 tokens/timestamps с ведущими ASCII-пробелами. В пункте3 word grouping должен учитывать реальные tokens, а не предполагать толькоSentencePiece`▁`; текущий runtime/планировщик не менялся.

## 2026-11-07T00:42:57+03:00 — пункт 3: выбор кандидата и ограничения приёмки

- Подбор выполняется только на dev. Прежде чем открыть результаты выбранного кандидата на holdout, завершаем заранее заданные варианты: исходный word-путь, seam и глобальные VAD presets. Кандидаты с dev normalized WER хуже baseline исключаются; среди остальных основной критерий — минимум raw WER, затем normalized WER, удаления на коротком dev и более простая конфигурация при равенстве.
- Два параллельных host-процесса используются для проверки качества; их RTF не сравниваем с одиночным baseline как скорость алгоритма. Финальный выбранный прогон должен выполняться отдельно.
- Словные границы — оценки по RNNT emission frames (40 мс), не forced alignment. Не добавляем выдуманные границы или padding под интервалы эталона. Цели −30% удалений и <200 мс показываем отдельно от primary WER gates; их непрохождение не скрываем.
- Ранний seam-профиль применял правку и к единственной группе чанка. Это шире требования §0.4 про разрез по спикеру. Исходные результаты сохраняются; после текущих прогонов профиль будет ограничен реально разделёнными чанками и повторён.
- Уточнение пользователя: LLM, Lite-APK и лендинг не выполняются до подтверждённой приёмки основного Android-конвейера. Текущая работа остаётся в D.

## 2026-11-07T00:45:38+03:00 — пункт 3: обязательная цель коротких реплик

В раннем описании выбора минимум raw WER стоял перед целевым снижением удалений. Это недостаточно учитывает явную приёмку задачи D в плане. До открытия candidate holdout уточняем: если dev-кандидаты одновременно улучшают raw WER, не ухудшают normalized WER и достигают −30% удалений на отмеченных коротких dev-кейсах, выбираем минимум raw WER внутри этой группы; затем normalized и простота при равенстве. Иначе лучший primary-WER кандидат остаётся только экспериментальным. Цель времени слов нельзя считать доказанной по coarse clip gold. Все кандидаты и исходный порядок записаны, ничего не удаляется.
