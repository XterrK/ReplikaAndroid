# Аудит V1.3 перед дизайном

Источник: реальные исходники на `ce345569377f0d7b60b383296f00f58b417986e0`, существующие Human Review, PROJECT_STATE, TEST_REPORT_V1_3, REAL_DEVICE_FINDINGS, DIARIZATION_FIX_REPORT, PERFORMANCE_ANALYSIS, пользовательское сообщение V1.4. Историческое сообщение о пяти минутах из REAL_DEVICE_FINDINGS не подменяет новое наблюдение пользователя (~30 секунд).

## Диалог

`TranscriptPresentation.groups` объединяет одного известного говорящего при паузе ≤1200 мс, длительности группы ≤45000 мс и тексте <1200 символов. `WorkspaceScreen` использует эти же группы в Dialogue и Reading. `LogicalDialogue` сохраняет исходные части, но отображает их внутри одного lazy item с одним speaker header. Следствия: гигантская единица прокрутки, редкие визуальные опоры, несогласованный вид одиночных и объединённых реплик. Исходные сегменты в Room не утрачены.

Предлагается отдельная плоская presentation-последовательность Dialogue по source ID; компактный заголовок на смене участника, точное время каждой исходной части, индивидуальная активность/seek/edit. Не разрезать искусственно ASR-сегменты на выдуманные времена. Для очень длинной исходной части возможен текстовый абзац без фальшивого timestamp. Reading продолжает использовать группы без inference.

## Почему «<700 мс» оказывается рядом с длинным интервалом

Подтверждённая цепочка в коде:

1. `Alignment.slices` создаёт объективные причины unknown/overlap и эвристику короткого интервала.
2. `RecognitionPlanner.plan` восстанавливает неизвестный край ≤300 мс с единственным соседним говорящим. Текст причины: **«Короткая граница диаризации: проверьте слова»**.
3. Planner объединяет соседние части одного говорящего, сохраняя union причин, но без локаторов исходного края. Таким образом причина короткой границы остаётся у, например, 0–6000 мс ASR slice.
4. Worker сохраняет этот slice и список строк причин в Segment/Room.
5. `SmartReview.reviewIssues` проверяет `reason.contains("Короткая")` и превращает обе разные причины в **«Фрагмент короче 700 мс»**. Текущая длительность не проверяется.

Дополнительное визуальное агрегирование в Dialogue возможно, но очередь Smart Review получает физические `SegmentRow`, а не LogicalTurn. Поэтому только снятием группировки этот дефект не исправить.

Детерминированный пример: VAD [0,6000], diarization [200,6000] speaker 0. Неизвестный край [0,200] восстанавливается, затем сливается с известной речью. Результат [0,6000], speaker 0, причина «Короткая граница…», UI утверждает «<700 мс». Это воспроизведено вызовом неизменённых production-классов после baseline build: `probes/WarningProvenance.java`, результат `evidence/warning-provenance-reproduction.json`. Соответствие именно пользовательским 17 предупреждениям требует его diagnostics JSON, отсутствующего в репозитории. Потерянное точное положение причины нельзя честно восстановить из уже сохранённой строки.

## Предлагаемая модель проверки

| Основание | Основная очередь | Формулировка |
|---|---|---|
| Текущий speakerId <0 | Да, если не проверено | Говорящий не определён; exact source range |
| Сохранённое пересечение | Да, с оговоркой | Анализ отметил пересечение; не утверждать истинность ML |
| Старое неоднозначное назначение при уже известном говорящем | Контекст назначения/диагностика | Текущее ручное назначение имеет приоритет; старый flag не означает новую ошибку |
| Длительность <700 мс | Только диагностика | Короткий сегмент сам по себе не доказывает проблему |
| Восстановленная граница ≤300 мс | Только диагностика без дополнительного доказательства | Не называть весь интервал коротким |
| Жёсткий ASR-разрез 20 с | Только диагностика без дополнительного доказательства | Граница обработки, не обнаруженная потеря слов |

Никакого confidence без данных. Никакого альтернативного ASR на каждом фрагменте. Не обещать точную вложенную границу для legacy данных без её provenance. Новую типизированную presentation-политику можно добавить без миграции Room и без изменения ML; формат новых локаторов требует отдельного решения после выбора.

## Другие findings для нативной реализации

- Unknown уже получает нейтральный цвет в `speakerColor`; нельзя заменять его первым участником. Текст, фильтр, editor и export должны использовать единый fallback.
- Активный сегмент выбирается `firstOrNull` по времени; при overlap возможны несколько активных частей. Нужна явная политика отображения пересечения и совпадение с timeline.
- `groups` многократно строит `p.text`, lookup активной строки и timeline обходят сегменты. Риск длинных записей следует измерить; это не доказанный jank.
- Follow scroll сейчас работает по группе, не исходной реплике. Flattening должен изменить индекс scroll без потери ID.
- Export читает Room в транзакции; оба режима должны экспортировать один snapshot с текущими исправлениями. Чистое копирование остаётся отдельным действием.
- `TranscriptModesV13Test` проверяет существование logical-turn; после утверждённого redesign нужно обновить ожидание структуры и сохранить поведенческие проверки.
- `ReviewScreenshotsTest.actualShortSpeechReviewQueue` требует старый короткий warning. Его нужно заменить содержательной проверкой новой политики, а не сохранять шум ради зелёного теста.
- Automatic diarization остаётся отдельной ML-проблемой: исторический four-speaker fixture дал 7 участников. Это не закрывается цветовыми метками.

Thermal API и JNI отмена с существующими ограничениями сохраняются. Не вводить зависимости ради эффектов до проверки официальных Compose API текущей версии.

План motion после выбора: короткий spring active rail, crossfade режимов с сохранением scroll, native sheet/IME insets, плавный draw-only playhead, однократное подтверждение сохранения. Уважать duration scale; без бесконечной декоративной анимации во время ML. FPS и отсутствие jank до замеров не заявляются.
