# API 35 AVD three-button navigation — external rendering limit

Observed on the existing `Replika35v11` AVD, image fingerprint `Android/sdk_phone64_x86_64/emu64x:15/AE3A.240806.019/12368160:userdebug/test-keys`. Scope is this old AOSP image, not all Android 15 devices or the disconnected vivo X300.

With Android's system theme LIGHT and REPLIKA manually DARK, the Activity requests native appearance mask 0, owns focus and draws correct `#111214` status/navigation backgrounds. The system status clock renders with contrast 18.74. SystemUI's LightBarController also computes `navigationLight=false`, `navbarColorManagedByIme=false` and dark intensity 0.0: it requests light navigation glyphs. The actual three-button Home glyph remains RGB `(69,70,79)`, contrast **2.001** against the graphite background.

The renderer is Launcher3's Taskbar window. Its live dump reports framework nav-button intensity 0.0, but `mOnTaskbarBackgroundNavButtonColorOverride=1.0` and override multiplier 1.0. The matching [AOSP implementation](https://android.googlesource.com/platform/packages/apps/Launcher3/+/refs/heads/android15-release/quickstep/src/com/android/launcher3/taskbar/NavbarButtonsViewController.java) computes a Taskbar-background override independently of the framework icon choice. Its background icon color comes from the Launcher context's system theme; a full override substitutes that color for the framework result. This agrees with the observed grey glyph. The AOSP source branch is supporting implementation evidence, not a bit-for-bit reconstruction of the installed Launcher binary.

The issue was reproduced manually outside JUnit, after Home/return, after restarting only Launcher3, and after a controlled cold host restart of the same AVD. A guest reboot initially stalled its ADB transport; the explicitly authorized host restart preserved the original userdata, app/model files and configuration. No wipe-data, pm clear, application-night-mode hack or global system-theme override was used. Emulator 5558 was not changed.

A separate temporary gesture-navigation check on the same app/theme produces a visible light handle, RGB `(236,236,237)`, contrast **15.875** on `#111214`. Restoring the original default three-button mode restores the low-contrast glyph and Taskbar override. Original navbar overlays were all disabled; that exact overlay state and mode 0 were restored. Final profile is 360×640, density 160, font scale 1.3; the original AVD configuration INI is unchanged.

The strict three-button contrast assertion in `ThemeBarsV15Test` remains at 3.0. It is not weakened or hidden by a fingerprint-specific assumption. The test additionally supports gesture-handle contrast and samples an empty navigation-background zone outside the handle. Thus the old AVD's three-button visual failure remains explicit while the gesture check can establish its own scope. An application cannot recolor another process's Taskbar internals through the public SDK.

Evidence: [external-taskbar-override.json](../../human-review/v1.5/evidence/theme-bars-build7/external-taskbar-override.json), manual screenshots and SystemUI/Launcher/window dumps in the same folder, plus the `host-recovery` configuration/process record. Primary 5556 was returned online with its original data and profile. Physical-device system-bar acceptance remains unverified.
